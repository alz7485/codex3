# 監査実行プロトコル

## 0. 起動・対象の固定

短い日本語指示をAGENTS.mdの3モードへ割り当てる。対象/版が指定されていれば優先する。AttendSyncとリポジトリルートの別製品を区別する。`scripts/audit_control.py resolve` は直接ソースか最新の完全版ZIPを選ぶだけで、コードの実行や展開はしない。

実行ID、モード、対象絶対パス、Trial番号またはcommit、SHA256、開始時のgit差分、採用仕様、基準版、OS/Python/依存、実サブエージェント機能と同時実行可能数を記録する。開始前のユーザーの未コミット変更を消さず、その状態を監査対象とする。実行ごとに専用の一時領域を作る。

ZIPは展開前にCRC・マニフェストを確認する。絶対パス、`..`、Windowsドライブ、リンク、重複ファイル名、異常な展開量を拒否し、作成した一時ディレクトリの外へ書かせない。親が同一のスナップショットを固定し、各担当はそれぞれのテスト用コピーを作る。全担当へ同じ版・ハッシュを渡す。テスト後に原本と製品コードのハッシュを確認する。原本の変更を検出したら報告に明示し、勝手に復元しない。

## 1. 並列編成

通常監査は以下の6グループを並列起動する。1グループ1エージェントで、両方の役定義を読み込ませる。各領域は重点確認と主要な実行試験を行う。

| グループ | 専門分野 |
|---|---|
| G1 仕様・構造 | 1 仕様整合性 / 5 アーキテクチャ |
| G2 不具合・耐障害性 | 2 バグ・例外 / 10 破壊的テスト |
| G3 操作性・改善 | 3 UI・UX / 11 改善提案・新機能発掘 |
| G4 性能・省力化 | 4 パフォーマンス / 9 自動化・省力化 |
| G5 データ・安全性 | 6 データ整合性 / 7 セキュリティ |
| G6 配布・独立反証 | 8 配布・環境 / 12 懐疑的独立監査 |

完成監査では1〜12を1役1エージェントへ分離し、各分野の実行経路、境界・失敗条件、関連試験、証拠を網羅する。実上限が6なら6件ずつ2巡する。処理済みスレッドが上限に算入される実装では利用可能なclose機能を使い、なければ完了済み役を新規独立タスクで再利用できるか確認する。再利用で過去所見が残る場合は独立性の低下を明記する。無理に12同時起動したり、未実施の役を実施済みとしない。

修正後監査は次を固定する。

1. 修正前/後のパス・版・ハッシュ、差分、元の指摘ID、変更理由。
2. 変更箇所、直接/間接依存、データ形式/設定/キャッシュ/履歴の互換性。
3. 元の再現ケース→修正確認、隣接境界、失敗復帰、既存機能の副作用。
4. 変更に対応する担当を並列起動。少なくとも仕様/実装確認、バグ/回帰確認、独立した懐疑的評価を含める。影響が広い/差分が不明なら6グループを使用する。
5. 元の再現条件が実行できなければ「修正確認済み」にしない。差分の基準を特定できなければ現状監査を続け、修正前後の比較は未検証として完成判定を保留する。

統括監査は各モードとも専門役の初回報告確定後に別エージェントで実施する。主担当が自分の結論だけを「独立統括」と呼ばない。親は統括と全役の結果が揃うまで集約を終えない。

## 2. 独立性・ツール適応

- 初回は共通の対象・仕様・条件だけを配り、他担当の所見を配布しない。 ホストが対応する場合は `fork_turns="none"`（または同等の履歴非継承設定）で起動し、役の指示と対象条件を明示的に渡す。親の全履歴から他の結論が混入するのを避ける。懐疑的役の独立報告が確定した後に他報告を見せる。
- 名前付き役が使える環境では `.codex/agents/<role>.toml` を選ぶ。使えなければTOMLの `developer_instructions` をタスク指示に含め、同じ役割を実ツールで起動する。通常グループは2役分の指示を併記する。
- 実行中のツール定義を優先する。このホストのspawnは `task_name` / `message` を使い、`agent_type` を受け付けない。環境によっては `agent_type` が使える。存在しない引数・ツールを仮定しない。
- モデル/推論強度は親の設定を継承し、今回の設定では変更しない。各担当の再委任は禁止し、親が上限を管理する。
- 各役へ、担当専用の出力先とJSON/Markdown報告テンプレートを渡す。担当の初回結論を保ったまま、再検証・反証は追記する。

## 3. コード無変更と実行試験

監査依頼では製品コード、既存テスト、依存、設定、配布物を一切修正しない。テストの成功率を上げるために期待値を変更しない。追加の検証コードは一時監査領域のみ。課題があっても改善案と必要な修正を報告するだけで終え、別の明示依頼なしに自動修正・コミット・push・リリースしない。

専門役はテストを一時コピーで実行し、原本は読み取りだけにする。Pythonは `PYTHONDONTWRITEBYTECODE=1`、GUI試験可能な環境では `QT_QPA_PLATFORM=offscreen` を使える。固定の `/workspace` や特定venvを前提とせず、利用可能なPythonと依存を調べて記録する。既存試験に原本/実データ/外部副作用がないか確認してから実行する。依存の追加インストールは監査と混同せず、既存環境で実行できなければ未検証とする。

AttendSyncでは単体解析だけでなく、実ReadWorker/キャッシュ、ID2種類とメール紐付け、年月境界・隠し数式0・空欄・秒、表示/全数/印刷/メール範囲、設定と結果のスナップショット、保存/復旧、部分実行・取消・二重処理を確認する。Outlookは模擬COMと合成データのみ使用し、実接続・実配送・Windowsビルドの結果を代用しない。

故障注入は一時ファイル・モックに限定する。実社員データ・実メール・実認証・秘密の表示・外部アプリ書込・実ユーザーディレクトリの破壊を禁止する。各自のプロセスを期限付きで管理し、共有環境の無関係なプロセスを終了しない。

## 4. 指摘の記録とクロスレビュー

すべての指摘にテンプレートの必須項目を付ける。重大度と確度は別軸とする。

- P0：直ちに運用を止めるべき広範なデータ破壊、重大な漏えい/誤送信など。実害条件と根拠を必須とする。
- P1：主要機能を阻害する重大な誤判定、データ消失、再現性のある危険な副作用。
- P2：条件付きの誤動作、回避策がある主要操作の不具合。
- P3：軽微な操作性、表示、保守性の問題。

確度は「再現済み / 静的根拠あり / 仮説 / 未検証」。改善/新機能は別表とし、未依頼機能を完成の阻害理由にしない。性能は測定環境と規模、UIは実操作と対象画面、セキュリティは脅威条件と到達可能性、配布は実際に検査した成果物を記録する。

統括はID対応表を作り、同じ根本原因を統合し、異なる症状は証拠として残す。矛盾は多数決でなく、対象版/設定/OS/期待仕様の違いを確かめ、証拠の再検証で裁定する。不明なものは消さず残存リスクにする。試験スクリプト本数、unittest件数、subTest条件、アサーション、再実行を合算しない。全員の「問題なし」を完成の根拠としない。

## 5. 完成判定

| 判定 | 条件 |
|---|---|
| 可 | 必須受入条件と重要経路を検証し、必要分野が実施済み。阻害する確定不具合がなく、重大な未検証もない |
| 条件付き可 | 検証範囲では阻害要因なしだが、実機/外部連携など未検証や明示した軽微な残存リスクがある。条件と対象範囲を列挙 |
| 不可 | 必須仕様不適合、P0/P1等の重大な確定不具合、原本保護違反などが残る |
| 判定保留 | 対象/基準/仕様の不足、専門分野未実施、重要試験不能、重大論点が仮説のままで判断できない |

完成判定の意味を「この版をこの条件で使う判断」として明記し、すべての環境/入力を保証しない。旧メール履歴のように情報が既に失われている制約も隠さない。最後に未解決ID、未検証事項、残存リスク、完成判定、必要なら次に確認する手順を提示する。修正は実行せず、報告後は明示的な別指示を待つ。
